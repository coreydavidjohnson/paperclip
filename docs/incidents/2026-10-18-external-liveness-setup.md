# External liveness setup can retain ownership or stall sweeps

Independent review of PER-1010 found two candidate-only P1 defects. No deployment or production impact was established.

Observer configuration resolution occurred after lease renewal started but before its try/finally. A rejected lookup abandoned the renewing watcher. Configuration resolution in the sweep was outside the probe timeout; a never-settling resolver retained the scheduler single-flight indefinitely.

Correction: put all observer setup inside lease cleanup and apply the existing ten-second operation bound to configuration lookup in probe, observe and stop paths. A timed-out resolver cannot resume provider execution after it settles late.

Rule: acquire renewable ownership only inside a cleanup scope; bound dependencies before entering a globally single-flight job.

Regression tests: heartbeat-external-observer-integration.test.ts covers rejected and hung setup followed by observe-only recovery. heartbeat-external-liveness-db.test.ts covers a hung lookup, a subsequent unrelated deadline, and injected failure in the real finalization outbox transaction.

Release remains gated on exact-revision full validation, independent re-review, and the parent staging/mixed-version drain checks.

Dependency follow-up: an assembled PostgreSQL test showed unresolved blockers retained the relation but reduced the liveness wake to a skipped diagnostic. Recovery context was not available to the later dependency wake. Queue admission now defers the original liveness receipt for dependencies as well as pending cards. Outbox redelivery rechecks gates before promoting a saved liveness receipt; stranded-wake admission retains its idempotency key so the same checks still apply. Concurrent outbox redelivery must retain one receipt, and resolution must produce one successor with predecessor/outcomes-unknown context.

Rule: a gate may postpone recovery, never replace its durable intent with a diagnostic receipt.

## Budget admission and replay boundaries (PER-1031)
Reproduced against exact 323d9ecf4fe103986de0e21e5cbcc3579654bffd with real embedded PostgreSQL, assembled heartbeat admission and a previously queued human comment. A spent project budget reduced the recovery wake to a replaceable execution-wait diagnostic and raised conflict. The durable liveness receipt was absent (one expected, zero found), so the finalization outbox retained dead issue ownership. This is a candidate defect; no production impact was established.
Merely persisting the recovery receipt was insufficient: release draining could discard budget-blocked work, and budget enforcement could fail its saved human input before or after wake delivery. The correction retains the original recovery reason and fresh-session safety context under the issue lock, treats a saved budget hold as delivered without authorizing execution, prevents direct release-drain promotion while that hold exists, and protects only matching agent/issue finalized recovery work from blanket budget cancellation. Periodic fresh admission advances the same liveness receipt, not a second intent.
The regression has resume, stop, terminal-cleanup-failure and lost-outbox-ack variants. PostgreSQL triggers fail the actual cleanup write or acknowledgment update after wake persistence. Retried and duplicate delivery plus periodic admission retain one receipt, saved human input and zero executions while blocked; lifting budget yields one successor with predecessorRunId, outcomesUnknown, forceFreshSession and the saved comment. A later explicit stop prevents that successor. A cleared executionRunId with a deferred recovery receipt is a deliberate policy hold, not an orphan lock.
Verified blocked/unblocked route lesson: active or unknown provider evidence must keep execution ownership; only confirmed gone permits fresh recovery. Gone recovery retains human input and safety context, while an unresolved dependency remains a deliberate hold. The existing route checks also release the stale observer after successor admission and assert that it cannot overwrite the predecessor or successor.
Verification history is retained in the task evidence: the original budget reproduction failed as expected. An intermediate implementation passed an undefined receipt ID to UPDATE when both optional IDs were absent; the focused regression run exposed the missing successor and active/unknown timeouts. Requiring an actual executionWaitRequestId corrected that branch. Fault-injection assertions were also corrected to match the persisted Drizzle query error wrapper, not its nested cause. These intermediate runs were not acceptance passes.
Rule: recovery safety context must be durable before terminal cleanup; a policy hold must preserve queued human input and remain eligible for fresh admission. Do not use finally(onTerminal) to hide a rejected recovery wake. Section 9.9 crash boundaries exercised here are finalization rollback (existing test), wake-persisted cleanup failure, and wake-persisted acknowledgment failure. Provider-wide outage with real tool effects, mixed-version rollout, real provider behavior and the parent exact-revision release matrix remain outside this child acceptance.

## Combined gate finalization and stale-predecessor follow-up

The disposable 20 GiB exact-c9135c411 image gate completed without OOM but failed three server assertions (1,023 server tests passed); 180 UI and 134 adapter-utils tests passed. This was a code/test failure, not another dependency-build memory failure. The earlier agents-host restart interrupted its coordinator; a later completed gate must not be confused with the canceled attempt.

The accepted completion increments observer_epoch. Instruction-copy cleanup used the original epoch when appending a warning, so a successful completion could suppress its own cleanup evidence. The coordinator now transfers cleanup-event authority only to the row returned by its accepted completion. A stale completion cannot acquire a newer observer's authority.

Two no-owner Stop/pause tests reached the cancellation readiness barrier later than their default one-second wait allowed. Their condition waits are explicit. After that correction, both reproduced a separate accounting defect: Stop won and advanced the epoch; the old executor returned proof that provider work never started, but the original-epoch update discarded that proof. The runtime now accepts only the exact direct-Stop settlement receipt at epoch E+1, and only before cost accounting has completed. It merges the no-work accounting flag without replacing Stop metadata or manufacturing usage. The completion fallback also leaves no-work Stop results intact. Four real-PostgreSQL cases check direct Stop, takeover-then-Stop, wrong receipt, and already-accounted exclusion.

The separate PER-1049 changes are merged while its stale-request ownership remains separate. Two further real-route regressions reproduced old deferred recovery replay after a newer predecessor completed. Current-generated cutoff skips are not adopted as legacy safety contracts. Under the issue lock, admitting the newer recovery binds older unbound deferred receipts to it only when those receipts carry neither queued human comments nor interaction delivery. Source run creation order establishes which predecessor is older. Old receipt evidence remains durable and cannot later start another recovery.

Fresh focused verification: seven cleanup/Stop/pause regressions passed (exit 0); 30 runtime-accounting and stale-recovery tests passed (exit 0). Server TypeScript passed before the additional four accounting tests; a subsequent candidate check is tracked separately. The earlier combined attempt was killed without an exit file and is not a pass. A diff-only Opus review found no definite defect in the Stop predicate; assumptions were checked against numeric epoch storage and the exact false-only provider-work branch. Review is not deployment approval.

Rules: transfer terminal cleanup authority only from an accepted completion; preserve Stop's exact result when recording no-work accounting; fence post-Stop writes by the original settlement receipt and one epoch transition; never supersede saved human input merely to suppress duplicate recovery. Real provider outage, mixed-controller rollout and staging acceptance remain parent release gates. Nothing in these focused results authorizes deployment.


## Post-terminal cleanup authority (2026-10-21)

The interrupted-run follow-up reproduced a lost cleanup warning with real embedded PostgreSQL: completion committed success and bumped the observer epoch, then lifecycle-event persistence threw before completeRun returned. Outer instruction cleanup used the old epoch and its warning was fenced out. The original result, cost and approval card survived; the warning assertion failed (0 instead of 1).

Correction: completion synchronously hands its actually persisted terminal row to the executor before accounting, liveness classification or lifecycle effects. Only the owned compare-and-set or exact receipt-fenced metadata write can grant this authority; do not replace it with an arbitrary latest-row read in finally. The regression injects both the post-terminal failure and outer cleanup timeout. All six cleanup variants pass on Node 24.22.0, with server TypeScript and forbidden-token checks passing. The first attempted test launch had a Python quoting error and selected no tests; it is not evidence. The subsequent red run selected one test and failed the expected warning assertion; green selected six and passed six.

Rule/test: transfer authority at the durable state boundary, not after fallible completion effects. Keep the post-terminal-failure matrix case in heartbeat-process-recovery.test.ts. A bounded Opus diff review reported no confirmed P1/P2; it is not release approval and does not prove real-provider staging or mixed-version rollout. Full exact-revision image validation is tracked separately by PER-1010; nothing is deployed by this correction.
